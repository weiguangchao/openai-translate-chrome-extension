# chrome-debug 修复高倍速下的重复拖动和漏算时间

[PR #30](https://github.com/weiguangchao/openai-translate-chrome-extension/pull/30) 做真实浏览器验证时，chrome-debug 在高倍速下有两个问题，都会让测出的指标失真。

1. `media` 带 `time` 时，拖动语句写在每次轮询都执行的探测脚本里，只要视频离目标超过 1.5 秒就再拖一次。YouTube 在 2x 下拖动后缓冲，视频一恢复播放就会走出这个范围，于是又被拖回去。在 `qp0HIF3SfI4` 的 600 秒处，两版构建分别出现了 89 次和 66 次拖回 600 秒的事件，旧版那一步 90 秒后超时。1x 到 1.5x 的 YouTube 运行也都在拖动后约 2 秒多出一次拖回目标的事件。
2. Subline 页面状态不变时每 2 秒（墙钟时间）发一次心跳，`worker_trace.py` 却把视频时间超过 3 秒的间隔当成暂停或跳转丢掉。1.5x 下一次心跳约等于 3 秒视频时间，2x 下是 4 秒，正常播放被成段丢掉。PR #30 的 YouTube 1.5x 播放 trace 播了 180 秒，只计入 53.8 秒和 44.4 秒。同一句字幕还会被拆成几句计数，"整句错过"的分母跟着变大。`trace` 步骤累计已播放秒数时，用的也是固定 3 秒的视频时间。

## 改动

- `media` 只主动拖动一次。之后视频时间只要在"目标前 1.5 秒"到"目标后 1.5 秒加上拖动以来按倍速能播到的位置"之间，就不再拖动。超出这个范围说明网站把视频带走了，这时才补拖，最多 3 次，再超出就以失败结束并说明原因。带 `time` 的 `media` 结果新增 `seeks`，即实际改动 `currentTime` 的次数。
- `worker_trace.py` 判断两条状态之间是否连续，改为看墙钟间隔是否不超过 3 秒，并且视频前进量不超过墙钟间隔乘以最大倍速 4 再加 0.5 秒。状态时长、句子是否中断、`trace` 步骤累计已播放秒数都用这一条规则。
- trace 统计新增 `counted`，即状态实际覆盖的视频秒数。`counted` 低于播放秒数的 80% 时，统计里标记 `sparse`，结束行末尾也会显示，以后心跳或阈值再出问题时能当场发现。

## 离线验证

用 PR #30 保存的 32 段 trace 原始状态事件重新统计：

- 1x 和 1.25x 的 16 段，计入秒数和"翻译中"占比前后最多差 0.1。
- 1.5x 和 2x 的 16 段，计入秒数占播放秒数的比例从 18%–98% 变成 93%–101%。YouTube 1.5x 播放 trace 的句数从 62 和 64 回到 23 和 23。
- 按新统计，PR #30 里 YouTube 2x 落点的"翻译中"占比是旧版 73.8%、新版 45.0%。原报告是 50.4% 和 76.6%，结论相反。

每段的前后对比在 [验证数据](assets/chrome-debug-high-rate-summary.json) 的 `recount_pr30_traces`。

## 没有解决的问题

`media` 要等确认开始播放才返回，落点 trace 随后才开始，这次比拖动目标晚 1.7–4.3 秒视频时间。这段时间里的等待没有算进"拖动后首句等待"，所以这一项仍然偏低，2x 下影响最大。可以让 `trace` 在同一步里先开始记录再拖动，这次没有改。

PR #29 的 [倍速验证](2026-10-09-chrome-debug-steps.md) 用的是同一套统计，1.5x 和 2x 那几行很可能也受第 2 个问题影响，但当时的原始 trace 没有保存，无法重算。
