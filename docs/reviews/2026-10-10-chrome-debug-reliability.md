# chrome-debug 采样与会话修复

最近的真实浏览器验证反复遇到统计跨 trace 累积、播放倍速被网站改回后未报告、隐藏字幕仍通过检查、超时后才返回成功，以及长步骤阻塞状态查询等问题。本次实施评审中的 1–4 项，只修改验证工具、测试和文档。扩展源码未改，使用 main `62ae573` 的构建，指纹为 `b4d4eee4c2f3`。

## 改动

1. 每段 trace 单独记录播放倍速和页面可见时间。先观察再恢复目标倍速，保留页面的 `ratechange`、`visibilitychange` 事件，因此短暂重置也会使数据失效。落点 trace 播放中离开目标区域时直接失败。
2. 字幕检查同时判断实际可见性和视口位置。页面探测使用剩余预算，预算耗尽后不再接受成功结果。采样完成、数据有效、性能达标分别报告，Provider 慢或没有成功样本不会触发自动重测。
3. 独立的 `measure.py` 按计划运行，逐步骤保存命令、统计和原始事件。它冻结构建、记录工具与构建指纹、保留每次失败、支持续跑，并恢复原来加载的构建。落点避开打开段及已请求字幕的范围。`verify.py` 可离线检查结果并计算指标。
4. Chrome 已接受连接时不再误报需要手动点击 Allow。执行长步骤期间仍响应状态查询，返回当前步骤和视频位置；CLI 断开后取消它的命令。断线、无响应与正在执行分别报告。

测量规则放在独立的 [使用说明](../../.agents/skills/chrome-debug/references/measurement.md) 和 [播放计划](../../.agents/skills/chrome-debug/checks/playback-plan.json) 中。chrome-debug 的交互命令保持通用，工具测试没有加入项目 CI。

- 修改前直接运行原有 7 个预期失败用例，得到 6 个失败和 1 个错误，确认问题可复现。
- 最终版本运行 `python3 -m unittest discover -s .agents/skills/chrome-debug/tests -v`，105 项全部通过，包含原有 7 个问题的正式回归测试。
- 浏览器测试覆盖落点途中跳走、倍速反复重置、隐藏字幕、预算耗尽、忙时状态查询和客户端退出。测量器测试覆盖构建恢复、断线恢复结果、续跑跳过已完成结果、输入指纹变化与原始事件隔离。
- `npm run check`、`npm run build`、`git diff --check` 通过。
- 真实 Chrome 长 trace 运行期间，5 次 CLI 状态查询耗时为 0.5724、0.6224、0.3203、0.1762、0.0947 秒，中位数 0.3203 秒。均返回 `running` 和当前 `trace` 步骤。

## 真实 Chrome 验证

每轮重新加载 Subline，先收集 45 视频秒的 `since: "open"`，再跳转一次到未缓存区域，收集 45 视频秒的 `since: "seek"`，随后继续播放并收集 180 视频秒。Chrome 保持前台，媒体静音。YouTube 首次 `media` 从 60 秒有人说话的位置开始。

等待时间采用 AGENTS.md 的公式。加载占比为 `loading / (loading + ready)`。Provider p50 和 p90 来自连续播放窗口内完成的成功请求，按 `sent` 到 `done` 的墙钟秒数计算，使用 nearest rank，不除以播放倍速。失败、中止和未完成请求单独计数；没有样本时显示不可用。

本次没有配置性能阈值，`performancePassed` 为 `null`。有效采样说明测量条件满足要求，并不表示字幕性能达到某个目标。不同视频、打开位置及 Provider 在不同时间的波动，也不适合用来推断倍速与耗时的因果关系。

12 组均完成，共 36 段有效 trace。每段报告的倍速都等于目标倍速，`visible` 为 1，且没有 `throttled`、`sparse`、`truncated`、`clockTruncated`、`clockMissing` 或 `rateMismatch`。每轮落点只跳转一次。工具指纹为 `7ddf0a92dd72`。

## 排除与恢复

Chrome 最初两次连接等待授权超时。用户点击 Allow 后连接成功，整批采样没有再次断开 Chrome 连接。

X 1x 第一次开场在 8.89 秒处持续缓冲，165 秒预算耗尽，只采到不足 9 秒的视频。工具报告未完成并标记 `throttled`，该尝试没有计入指标。自动重试重新加载扩展，随后三段 trace 全部有效。其余 11 组首次采样均有效，没有因 Provider 表现较差而重测。

全部结束后，测量器恢复原构建文件并成功重新加载，恢复指纹仍为 `b4d4eee4c2f3`。会话创建的标签页全部关闭，holder 已停止。

## 本次数据说明的问题

YouTube 1.25x 连续播放加载占比为 30.2%，同时有 2 个 `error` 和 6 个 `aborted` 请求；成功请求的 p50/p90 为 1.98/3.02 秒。只看成功请求的分位数会遗漏这段字幕体验变差的事实。新工具保留这组有效数据，性能是否接受交由阈值或人工判断。

X 2x 连续播放加载占比为 56.4%，落点加载占比为 43.2%。播放窗口有 19 个成功请求、24 个中止请求和 2 个未完成请求，成功请求 p50/p90 为 3.13/7.13 秒。后续若改进字幕性能，应优先检查这两组的错误和中止原因；本次数据只能证明它们同时出现，尚未定位扩展中的具体原因。

本次没有修改扩展翻译逻辑，不能把两次采样间的字幕性能差异归因于工具修复。改进体现在错误采样的识别、原始证据保留、恢复流程和会话响应上。
