### A. 缓存和任务必须按各自寿命管理

**历史证据。** 重放 `6a2922f` 的缓存测试：旧版本在 Provider 退避时连已翻译的字幕也不能返回，新版本正确返回缓存。重放 `d7a3d88` 的 YouTube 源缓存测试：旧版本只改目标语言就从一次下载变成两次，新版本在目标语言、Provider、样式、签名和 blob URL 变化下复用原文。

**当前缺口。** `src/extension/background.ts` 的 storage listener 对任意设置变化都调用 `queue.reset()`；`src/core/controller.ts` 的 `update()` 也总是 unmount。新增隔离探针确认：进行中翻译的 AbortSignal 初始为 false，只把字号改为 36 后变为 true。它不否定已有“完成译文不失效”测试，而是说明那组测试没有覆盖正在付费等待的请求。

**决定。** 保留 `SourceCache`、`TranslationQueue`、`CaptionTranslator` 的现有分工，不创建另一套缓存或通用状态机框架。在 shared 定义设置变化的分类函数，由 background 根据前后完整设置生成变化类别；跨边界只发送类别/不透明的翻译配置版本，不发送 API Key、Base URL 或它们的拼接缓存键。content 按类别更新；样式有独立 `SubtitleOverlay.updateStyle()` 路径。

| 事件                           | 源字幕                             | 已完成译文                         | 进行中翻译和显示                                          |
| ------------------------------ | ---------------------------------- | ---------------------------------- | --------------------------------------------------------- |
| 字号、颜色、背景、间距         | 保留                               | 保留                               | 保留请求，原地更新样式                                    |
| 目标语言、模型、Provider、凭据 | 保留                               | 按已有配置键隔离，可保留旧配置结果 | 取消旧配置工作，切换显示版本                              |
| 源语言、源轨道、视频变化       | 替换相应 source identity           | 按原有翻译键处理                   | 释放该消费者的旧需求，晚到结果不得覆盖新画面              |
| pause                          | 保留                               | 保留                               | 不启动新任务；已发送任务允许完成，保持现有语义            |
| seek                           | 保留                               | 保留                               | 保留已有 settle/lead 策略，取消不再被任何消费者需要的工作 |
| 关闭扩展、离开页面             | 完成的源缓存按现有页面生命周期处理 | 不主动清空后台完成缓存             | 停止相应消费者，恢复原生字幕；pagehide 释放页面资源       |

外部读取 source 状态改为只读快照/只读 getter，状态写入留在拥有者的方法内。不要把所有 `reset()` 简单删掉：配置变化、关停、换集仍须取消旧任务。

**验收。** 上表成为参数化场景。每例同时断言实际下载/Provider 次数、AbortSignal、源或译文内容；多消费者共享工作时，释放一个消费者不得中止另一个仍需要的请求。用不同原文和不同译文确认晚到结果被丢弃，不能只断言“没有抛异常”。

**层级理由。** 这是状态所有权问题，架构能够消除宽泛重置入口；类型只能描述配置字段，不能独自保证异步先后顺序，所以在单一入口后保留行为测试。

### B. 让字幕语义随数据一起传递

**历史证据。** `477622e` 前，8 条短字幕后接一个分成 3 条的长句，无法按新的整句迁段约束组成 `[8]` 与 `[3 + 后续]` 两批。`0e4aaaf` 前，同一条 HBO 多行字幕没有像 YouTube 一样形成两个完整句子；修复后得到 `Oh, thank you.` 和 `I've got to talk to that mailman.`。两组原提交测试均已重放红→绿。这是跨入口语义未统一的证据，不能证明这些约束在所有早期版本都已被明确要求。

**已有成果。** `core/sentences.ts`、`core/timeline.ts`、`core/overlay.ts` 和 `Platform` 已经集中处理大部分逻辑，应沿用。`6b865e8` 的分层是治理基础，不应另起一轮大重构。

**决定。**

1. 把 `texts[] + segments[] + needsSplit[]` 改成只读 `PrefetchItem[]`，每个对象携带 text、segment 和 split 信息。从 `captionWindow` 到 translator、消息解码、background 去重、queue 全程传同一对象结构。去重保留结果到输入的显式映射，不能分别 filter 三个数组。
2. 在现有时间轴构造入口区分源句、输入字幕、Provider 显示子字幕；批次 ID 只在序列化请求时生成。80 列本地目标、Provider 320 列验证余量、10 条输入限制分别保留各自含义，禁止按 Provider 输出条数重新计算 segment。
3. `CaptionFrame` 使用可辨识联合：普通字幕可直接显示原文；需要 Provider 切分的状态必须具备时间轴 cue，未 ready 时没有可显示的整句原文。显示子字幕必须由已验证的 TranslationPart 与原始时间生成。结构类型不能证明时间递增和完整覆盖，这些继续由现有校验函数负责。
4. 保留单一 overlay 和公共句子处理入口。补全依赖检查的动态 import 和任意 `src/platforms/<id>/` 覆盖，报错直接指向 `src/core/platform.ts` 的适配接口或 `src/core/sentences.ts` 的共享实现。无需为两个现有平台引入 workspace/package 系统。

**验收。** 保留上面两个历史样例，加上 >10 个 input 的单句、重叠 HBO cues、DOM-only、不完整/重复 Provider ID、Provider 输出 >10 条、切分结果晚到和缓存异步返回。错误输入类型的编译夹具应失败；使用 TypeScript 编译器 API 检查诊断，避免依赖本仓库禁止的 `@ts-expect-error` 注释。

**层级理由。** 公共实现已经存在，剩余主要是调用者可以构造互相矛盾的数据，故优先缩小 API 并强化类型；不再靠三份平行列表加更多长度测试。动态模块依赖仍可在 TS 中合法表达，所以还需 lint。它们是类型无法覆盖的补充，不替代公共实现。

### C. 给实际 HTTP 发送限流，而非给 `queue.run()` 限流

**复现。** 同一模拟时刻启动 3 个逻辑任务，实际 `fetch` 次数如下。所有网络响应均为本地 mock，没有真实请求或计费。

| 实现      | 触发条件                                 | 同一时刻实际 HTTP 次数 |
| --------- | ---------------------------------------- | ---------------------: |
| `162b9bb` | 4 个本地分片，批次结果无效，内部逐条回退 |                     15 |
| `9477089` | HTTP 400 触发参数兼容重试                |                      9 |
| `774dd06` | HTTP 400 触发当前 4 步兼容探测           |                     12 |

现有 `translationSendsPerSecond = 3` 和对应测试约束的是 queue 的启动次数。上述证明其不能成为实际 Provider 流量的上限；不是在指责预取段数的产品调整。

**决定。** 在拟新增的 `src/shared/provider/transport.ts` 集中执行 Provider HTTP；实际 POST `/chat/completions` 前取得发送名额。字幕首发、400/422 兼容探测、无效项单次纠正重试、连接测试走相同预算。扩展以 Service Worker 内唯一 transport 为拥有者，浏览器设置页的独立预览按自身执行上下文管理预算。GET 模型列表不占翻译 POST 名额。

queue 继续负责字幕优先级、消费者共享、取消和 segment 分组，把 HTTP 发送频率计数从 queue 移走。保留当前滚动 1 秒最多 3 次的规则；不同时擅自增加并发限制或改变两段预取策略。等待发送名额期间必须可取消，取消后不得启动 fetch。每次 HTTP 的 60 秒超时从实际发送开始计算；保留现有重试次数，不把“每次超时”偷偷改成另一种总超时策略。

限制 Provider 模块中绕开 transport 的直接 fetch；平台下载字幕的 fetch 是不同责任，不受该禁止规则影响。错误示例：`Provider POST must use src/shared/provider/transport.ts; retries also consume a send slot.`

**验收。** 上表转成 fake-clock 测试，断言任意滚动 1000ms 内实际 POST ≤3；推进时间后所有仍需要的工作必须继续并完成，避免用“不发送任何请求”通过测试。还覆盖排队时取消、多个消费者、兼容探测与纠正重试组合。将历史旁路调用作为 lint 的负例，标准 transport 调用作为正例。

**层级理由。** 限流必须覆盖所有发送入口，架构可以做到。仅增强 queue 测试或给重试加注释，未来新增的 API 内部回退仍可绕过它。

### D. 完整响应只选择和发布一次

**历史证据。** `9477089` 和 `7a41406` 是两次独立的兼容补充，说明“请求采用 OpenAI 风格”并不能保证所有模型返回同一正文外形。`2870488` 已将字幕统一到 `translateCaptionBatch`。重放 `7a41406` 的 GLM fixture，旧版本返回 null，新版本返回两条有序译文。

**当前缺口。** `src/shared/api.ts` 先通过 `onText → scanTranslationResults` 发布，再执行 `parseModelJson`。输入为“草稿 results JSON + Final + 最终 results JSON”时，`parseModelJson` 正确选择最后一份，但先发布的 ID 已进入 accepted，最终译文被忽略。隔离探针同时断言返回值和发布回调，二者目前都是“草稿”。这是确定的内部不一致；没有证据说明该特定文本在真实 Provider 会出现多少次。

**决定。** 保持完整非流式响应，删除字幕流程的提前扫描发布入口。按唯一顺序处理：提取正文 → 选择 JSON payload → 将支持的外形归一化 → 对齐 ID → 逐项验证 → 发布通过验证的项。沿用当前 `parseModelJson` 对完整响应选择最终 payload 的策略；若要保留截断 JSON 的已完成项恢复，将它作为完整解析失败后才调用的纯解析 fallback，选定一次候选集后再发布，不允许另一条回调先写 accepted。

每个输入仍可独立成功：同次响应中的有效项立即发布，无效项独立重试一次。保留字符串 ID、乱序、单条/批次统一入口和兼容外形；拒绝有歧义的 ID，不凭部分列表猜一基/零基。Provider 使用 `unknown`，只有校验成功才能形成内部结果。用于“测试连接”的自由文本翻译保留单独用途，但字幕 queue 禁止调用它。

**验收。** 当前双 JSON 探针修复后必须通过；GLM、content 文本数组、think/fence、单条、混合普通与切分输入、重复/缺失 ID、部分有效结果与取消均经过相同入口。错误 fixture 不能因放宽验证而被缓存。Provider 320 列余量沿用已有契约，不在这次治理中重新定义。

**层级理由。** 两条解析路径属于可删除的结构性问题；模型输出本身无法由本地 TS 类型保证，所以归一化后的运行时验证和真实外形 fixture 必不可少。

这些决定已在方案中确定：保留非流式、每次 HTTP 60 秒、两段预取、已有 80/320 显示列规则、SourceCache 和后台完成缓存；不引入全局框架、完整包拆分、缓存持久化、新的播放阻塞或凭据下发。平台注册表/manifest/build 的手工同步存在维护风险，但没有两次漏配的证据，暂不把“生成全部配置”塞入高优先级改造。没有依据把轮询开销或性能下降归因于特定提交，也不为此新增未经测量的优化项目。
