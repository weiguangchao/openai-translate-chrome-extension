# 拼接后超过三行的句子在送给 Provider 前切开

HBO Max 和 X 的 WebVTT 字幕经常没有句末标点。本地把字幕片段重新拼成句子时，只在句末标点处断开，所以会拼出很长的句子：

- X 测试视频的字幕里最长一句有 1310 列、85 秒；
- HBO Max《老友记》的片头曲被拼成一句 508 列、55.6 秒。

每个长句作为一个输入送给 Provider，请求要 10–22 秒才返回，常常在句子结束时被中止。

## 改动

- **切开过长的句子。** 拼接后仍然超过 240 列（三行显示）的句子，切成几句、每句不超过 240 列：
  - 优先在字幕片段之间或子句标点处切；
  - 单个片段本身超长时，再在单词之间切；
  - 切出的段数尽量少，长度尽量均匀。

  三行以内的句子保持不变，所以 TED 这类常见的三行长句仍然整句翻译。

- **切点规则复用显示断行的逻辑。** `fitLines` 增加了 `limit` 和额外断点两个参数，字幕片段的起点作为额外断点传进去。这套逻辑替换了原来按 5000 字符切请求窗口的做法。
- **测试：**
  - `githubCaption` 夹具去掉了结尾的 "instead of minutes"，从 256 列降到 237 列，继续作为三行以内的长句，用来测试显示拆行。
  - 680 列的列表和 7000 字的转写这两个测试，改为断言新规则。
  - 新增一个测试：人工字幕按片段之间切开。
  - `npm run verify` 全部通过，包括 385 个单元测试和 53 个端到端测试。

- **X 1x 改善明显。**
  - 拖动后等待：12.7 秒 → 3.1 秒。
  - 落点"翻译中"占比：33.3% → 5.9%。

- **X 1.25x：** 打开和拖动后的等待都从 10 秒左右降到 3–4 秒，但落点的"翻译中"占比反而更高。

- **对其他内容基本没有影响。** 这一集只有片头曲一处超过三行；YouTube 的 TED 演讲里超过三行的句子也很少，1x 播放段的句数只从 28 变成 29。这些行里两版的差异和 Provider 的波动在同一个量级。
  - 例如 HBO 1x 新版打开那一段漏了 14 句：那里都是短对白，没有句子被切开，原因是两组请求分别用了 10.5 秒和 27.3 秒。
  - HBO 1.25x 的 main 那一轮 Provider p90 达到 13.2 秒，所以数字特别差。

## 没有解决的问题

- **X 在 1.5x 和 2x 下仍然很差，两版都一样。**
  - 240 列的一段大约是 11–16 秒语音，这样一段的请求要 5–13 秒才返回。2x 下，这相当于 10–26 秒视频，句子在译文回来前就过去了。
  - 新版 2x 打开的那一段，4 个请求全部被中止，45 秒里一句译文都没出现。
  - 阈值降到 160 列（两行）时，X 最长一句只有 13.5 秒。这个方案在真实浏览器里只测到 1.5x 的打开和落点两段，就因为电脑睡眠、Chrome 断开连接而中断了，数据不完整，所以没有采用。
- **单轮数字波动很大。** 每个倍速每版只测了一轮，数字主要取决于落点附近那一两个请求的耗时。
