## SPA frame evidence limit

The current case at e2e/caption-sources.spec.ts:38 uses hold=true for every Provider request. It switches videos before releasing any opening route. The first video can show loading, but it cannot have a ready original/translation pair. Deleting a source invalidation clear therefore cannot leave the old ready pair visible, because no such pair exists. Page-video changes also unmount/reset at src/core/controller.ts:166, and a different caption text creates a fresh caption in CaptionTranslator.show, so deleting one clear does not bypass all invalidation paths.

The added interval starts before switchVideo and checks every visible source recorded with id=second, plus the existing later-frame rejection of the first translation. These checks positively demonstrate the new-video pair and would catch wrong pairs if such a frame were produced. They do not establish an independently exercised ready-pair clearing regression. The ledger recommendation to mutate clear for an old ready-pair flash should not be reported as validated for this scenario.

The existing scenario remains valuable as packaged adapter/runtime/worker replacement proof. It creates old held HTTP, requires exactly new-video demand, releases the new route, observes the new pair, then releases the old route and verifies that the new pair remains. Under the current owner path, unmount/release and queue prune abort old HTTP. Route fulfillment after browser cancellation need not deliver an old successful runtime reply. Neither this case nor withPlayer asserts a required aborted network request or aborted trace event, so it also does not independently require cancellation itself. A missing abort alone can remain safe because jobs and captions are independently identified.

No single reachable owner-guard removal was found that the added SPA frame assertions uniquely detect while the baseline final/later-frame proof passes. No new browser case is needed for preserving this historical contract. Keep the added interval as an observation with a successful new-pair control, and document the boundary. Do not present it as successful mutation proof for an old ready-pair flash or for a delivered stale callback. Controlled callback invalidation remains at the shared controller owner, such as tests/controller.test.ts:231, where the old reply is explicitly delivered for the same caption after seek invalidation.
