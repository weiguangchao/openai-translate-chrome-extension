# chrome-debug 改为逐步控制标签页并支持倍速

AGENTS.md 的 Verifying 一节要求在 1x、1.25x、1.5x 和 2x 下测量真实浏览器指标，但 chrome-debug skill 写着 "Read playbackRate. Do not set it."，无法测 1x 以外的倍速。检查还是写死的步骤列表，跑完就关标签页：YouTube 跳回上次播放位置、trace 被节流时，Agent 只能等整轮结束再重跑。`reload` 也只能重载 Chrome 已加载的文件夹，对比新旧构建时要手动覆盖 `dist`，加载失败也不容易发现。

## 改动

- `open`、`do`、`close` 让一个静音标签页在多次调用之间保持打开，Agent 每执行一步都能看到结果再决定下一步。`run` 保留，用同一套步骤重放固定检查。标签页 15 分钟没有请求会自动关闭，`stop` 也会关闭本会话的所有标签页。
- `media` 统一处理拖动、倍速、播放和暂停，并返回视频状态。页面有 YouTube 播放器时通过播放器接口设置倍速，之后的步骤里持续保持；关闭标签页时恢复原来的倍速。自动续播和跳过广告改为 `keep_playing`、`skip_ads` 两个开关，默认关闭。
- `wait`、`overlay`、`requests`、`focus` 取代原来的 `play`、`seek`、`wait-overlay`、`network-any`。`focus` 把 Chrome 和标签页切到前台，会抢走用户当前应用的焦点。
- `reload` 输出构建指纹，`--from` 先把另一份构建复制进 Chrome 加载的文件夹再重载，复制后校验指纹一致。
- SKILL.md 只写能力和安全边界，删掉了任务策略。

## Skill 自身的验证

- 离线校验步骤参数：冲突字段、类型错误、超出范围的倍速、相对路径和未知动作都会被拒绝。
- `reload` 能在两份构建之间切换，指纹分别为新版 `6a634a9fae60` 和旧版 `39736c394e09`；没有 `manifest.json` 的文件夹被拒绝。
- 在用户的 Chrome 里逐步执行 `focus`、`media`、`wait`、`overlay`、`requests`、`trace`、暂停和 `close`，结果都符合预期，关闭后的标签页再收到步骤会报错。
- 设为 1.5 倍并拖动后，之后的等待和 trace 里倍速保持不变，复测见下一段。关闭标签页后新开 YouTube 页面，视频和播放器倍速都是 1。
- `run` 批量模式重跑 `checks/smoke.json`，YouTube、HBO Max、X 三项都通过。

第一次 1.5 倍测试时，视频的 `playbackRate` 每秒被改回 1 一次，`defaultPlaybackRate` 也一起被改。在页面里拦截 `playbackRate` 的 setter 只抓到 YouTube 播放器自己设置的 1.5，改回 1 的调用来自页面之外；Subline 不写 `playbackRate`。用户停用 Chrome 里的一个倍速类扩展后复测，20 秒内页面只记录到设置 1.5 倍那一次变化，视频前进 30.3 秒。在这之前测的四轮 1.25 倍和 1.5 倍数据实际在 1 倍和目标倍速之间来回切换，没有计入；其中旧版在 1.5 倍下发了 172 个请求、中止 143 个，这是倍速反复变化导致的，不代表旧版正常表现。

## 用新 skill 重跑的浏览器验证

按 AGENTS.md 的 Verifying 一节，在用户的 Chrome 中用 `open`、`do`、`close` 交替测量旧版 `7708ec0` 和新版（PR #28）的构建。每个倍速用一段此前没有翻译缓存的 TED 演讲，两版各占一段，轮流先测。每次运行先 `focus`，播放后拖动一次并设倍速，立即记录 45 秒落点 trace，接着记录 180 秒播放 trace。计入的运行都满足：两段 trace 报告的倍速等于目标倍速，没有被标记为 `throttled`，落点 trace 从拖动目标后 5 秒内开始。

| 1x    | 新版 | `arj7oStGLkU` | 0%                    | 0.5 秒             | 0.5%                  | 0 / 27   | 31（1）      | 5.7 / 12.1 秒           |

1x 和 1.25x 下新版播放时几乎没有"翻译中"，旧版分别为 15.0% 和 42.6%。新版 1.25x 的落点阶段较差，是因为落点后两句长句分别用了 14.8 秒和 20.3 秒才返回，这时缓冲还没建立起来。

1.5x 和 2x 下两版都跟不上。新版在落点 45 秒之后的所有请求发出时两个在途名额都已占满（1.5x 18 个中 18 个，2x 31 个中 31 个），发出时余量的中位数只有 10.7 秒和 3.9 秒；1x 和 1.25x 对应为 37.6 秒和 29.8 秒，名额占满的请求只有 8/21 和 16/22。也就是说，倍速升高后瓶颈变成了"最多两个在途请求"的吞吐上限，提前量规则本身已经来不及发挥作用。1.5x 这组新版那轮的 Provider 耗时中位数是 10.2 秒，旧版那轮是 4.0 秒，两版的差异不能只归因于调度。在途上限随倍速提高，或者在余量不足时让每个请求装更多句子，可以作为 PR #28 的后续改进。

每轮的指标、请求统计、可见比例和未计入的四轮保存在 [验证数据](assets/chrome-debug-rates-summary.json)。
