# 人工浏览器验收

这里记录人在真实浏览器里对 Subline 做的验收：稳定用例、每次运行的结果、以及该次运行的截图。`npm test` 和 `npm run verify` 仍负责自动化检查。一次手动运行通过，只说明该次写明的 SHA 在写明的步骤上通过。

## 目录

| 路径 | 作用 |
| --- | --- |
| [cases.md](cases.md) | 长期用例库。本轮实测用 `TC-` 编号；确认缺陷用 `SL-BUG-`；从历史修复提取的回归用 `SL-REG-`。 |
| [runs/](runs/) | 每次运行一份记录，文件名 `YYYY-MM-DD-<测试 SHA 前 8 位>.md`。 |
| [assets/](assets/) | 与运行记录同名的截图目录。只放该次运行的真实截图。 |

已有运行：

| 运行 | 测试 SHA | 结论规模 |
| --- | --- | --- |
| [2026-11-11-dba68d08](runs/2026-11-11-dba68d08.md) | `dba68d08f7b48178a7ae208f18ff5dba84317df4` | 12 条用例，1 个确认缺陷（[#161](https://github.com/weiguangchao/openai-translate-chrome-extension/issues/161)） |

## 状态

用例库里的状态用下面这些词。一次运行记录里的 `pass` / `fail` / `partial` / `blocked` 与「通过 / 失败 / 部分通过 / blocked」一一对应。

| 状态 | 含义 |
| --- | --- |
| 通过 | 这一次运行实际做完了该条步骤，并且逐项验收都成立。代码已合并、单元测试在 CI 里通过，都不是这一状态。 |
| 失败 | 这一次运行做了该条步骤，验收不成立。 |
| 部分通过 | 写明的检查里，做到的那些成立，但范围没有覆盖整条。不要改记成通过，也不要据此关闭关联 issue。 |
| 部分失败 | 同一条里有的验收项失败、有的成立。把失败项写出来。 |
| blocked | 步骤没有做到可以下结论的那一步。站点登录墙挡住时写 blocked，并写明这不是产品缺陷。 |
| 未测 | 这次没有执行。不要补写结果。 |
| 不适用 | 产品已经没有这条路径，或后续改动使旧验收不再适用。写明原因。 |
| 历史来源待实测 | 步骤来自修复提交、测试或 PR 说明，当前产品上还没有按本条人工复验。不要因为修复已经进 `main` 就写成通过。 |

设计建议和信息架构建议不是确认缺陷。确认缺陷要有问题、步骤、验收，并关联 issue。

## 发现一条缺陷之后

1. 更新或新建关联 issue。本目录不代替开 issue。
2. 在 [cases.md](cases.md) 写入至少问题、编号步骤、逐项验收。同一症状更新原编号，保留发现版本，把新的结果追加到历史运行。不给同一症状再发一个编号。
3. 有截图或日志时，放进当次 `assets/` 并在用例里链接。没有图就写「未留截图」。
4. 新建一份运行记录，追加这次的实际结果和状态。已有运行文件不改原结论。
5. 只有这次真的按步骤做了，才把状态写成通过。

## 条目格式

每条以 `## 固定ID 标题` 开头。标识用本仓库的 `TC-`、`SL-BUG-`、`SL-REG-`。已发布的标识不改名、不复用。

元数据按这个顺序：

- 优先级
- 类型：功能缺陷，或体验改进。环境确认和播放冒烟写回归检查，避免把它们写成缺陷。
- 发现版本
- 最近实测结果
- 状态

正文按这个顺序：

**问题**

**前提**

**步骤**

1. 编号步骤

**验收**

- [ ] 每一项都能在画面或明确的测试断言上核对

来源 commit、PR、截图和历次运行结果写在验收之后。从历史提取、但点击路径不完整时，写明「历史来源推导、待补充」，不要写成已经人工复现。

新条目追加到 [cases.md](cases.md) 对应分区的末尾。验收标准若改变，在该条下追加修订日期，保留旧验收原文。

## 运行记录怎么追加

1. 先记下实际测试的完整 SHA、manifest 版本、产品名、日期、时区和环境。SHA 以当时检出并加载的提交为准。
2. 新建 `runs/YYYY-MM-DD-<SHA 前 8 位>.md`。已有文件不覆盖、不改写原结论。
3. 对用例库里这次执行过的每条，写上 `actual`、`status`、缺口，并链到 `assets/YYYY-MM-DD-<SHA 前 8 位>/` 里的截图。
4. 这次没跑的条目标 `not-tested`，或放在本次缺口里并说明没有结果。
5. 没有截图的条写「未留截图」，不补图、不复述想象中的画面。
6. 发现旧记录笔误时，在该文件末尾追加「更正」小节，写明日期和原因，原段落保留。

运行记录开头固定这些字段：测试 SHA、版本、日期、时区、环境、网络是否确认、性能是否重测。性能数字只来自当次测量。一次运行没有重测性能时，不抄另一轮的数字。

恢复成界面上的默认外观时，写当时看到的值。没有改之前的对照截图，就不要把恢复后的值写成原始状态快照。

## 缺陷记录

每个确认缺陷在当次运行记录里单独成节，包含：问题、复现、修改建议、验收、截图。修改建议标明「尚未证实为根因」。验收清单里，本轮没测的项保持未测，不写成失败，也不写成通过。

截图分两类，图注必须写明：

- 真实截图：浏览器里直接截下的画面。
- 裁切标注：同一帧裁切后加框或编号。图注写明来源文件，并写明画面内容未改。标注不是修复稿。

引用到 GitHub issue 时使用引入这些文件的提交上的永久链接，例如：

`https://raw.githubusercontent.com/weiguangchao/openai-translate-chrome-extension/<提交 SHA>/docs/qa/assets/<运行目录>/<文件名>`

或：

`https://github.com/weiguangchao/openai-translate-chrome-extension/blob/<提交 SHA>/docs/qa/assets/<运行目录>/<文件名>?raw=1`

仓库内的文档使用相对路径。不使用 `file://`。文档链接 issue 时不写会自动关闭 issue 的关键字。
